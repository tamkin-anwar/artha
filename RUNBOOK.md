# Artha — operational runbook

For anyone who needs to keep Artha running, or figure out why it's down,
without the person who normally maintains it. Written 2026-08-27. No secret
values live in this file, or anywhere else in this repo — see "Environment
variables" below for where they actually live.

## What's live, and where

- **App**: [arthaapp.com](https://arthaapp.com), a Python/Flask service
  hosted on Render.
- **Code**: this repository. Render deploys automatically from `main` on
  push — there's no separate manual deploy step for a normal code change.
- **Database**: Postgres, managed by Render, reached through the
  `DATABASE_URL` environment variable. Local development uses SQLite
  instead (see `README.md`); the two are not interchangeable for anything
  Postgres-specific (see the Boolean-migration note below).
- **Email**: transactional email (password reset) sent through Resend.
- **AI**: the AI Assistant and the bank-statement-import AI fallback both
  call the Anthropic API directly.
- **Push notifications**: Web Push, signed with a VAPID keypair.

### Deploy configuration lives in Render, not in this repo

There's no `render.yaml` or `Procfile` here — the build command, start
command, and every environment variable are set directly in Render's own
dashboard. That's a real gap, not just a technical detail: if Render
dashboard access is ever lost, the exact deploy configuration isn't
recoverable from the code alone. The app is a standard `gunicorn`-served
Flask app (see `wsgi.py` and the `gunicorn` entry in `requirements.txt`),
and a pending database migration runs as part of deploy (see the
Boolean-column note below for why that step matters) — but the *exact*
commands and flags Render is actually configured to run should get written
down somewhere durable (this file, once someone can see the Render
dashboard to confirm them) rather than staying dashboard-only indefinitely.

Confirmed from the web service's own deploy logs (2026-09-22):

- **Pre-deploy command:** `flask --app wsgi db upgrade`. This is the step
  that applies a new migration on every push. A failed migration shows up
  here, before the new version ever goes live.
- **Workers:** Render sets `WEB_CONCURRENCY=1` by default, so gunicorn runs
  a single worker. That matters for rate limiting: Flask-Limiter uses
  in-memory storage (see `artha/extensions.py`), which is only accurate
  with one worker. Raising the worker count would multiply every limit,
  including the AI spend limits, by the worker count unless a shared store
  (Redis) is added at the same time.

The exact build and start commands are still dashboard-only.

## Environment variables

Set in Render's dashboard (Environment tab), never committed here.

| Variable | Purpose | If it's missing |
|---|---|---|
| `DATABASE_URL` | Postgres connection string | App won't start |
| `SECRET_KEY` | Flask session signing | App won't start |
| `ANTHROPIC_API_KEY` | AI Assistant, statement-import AI fallback and categorization | Those features fail gracefully (a plain error or a silent skip); everything else keeps working |
| `ARTHA_AI_MODEL` | Optional override of which Claude model the AI Assistant uses | Falls back to a built-in default |
| `ARTHA_AI_TIMEOUT_SECONDS` | Optional override of the AI request timeout | Falls back to 45 seconds |
| `RESEND_API_KEY` | Sending password-reset emails | Password reset breaks |
| `RESET_EMAIL_FROM` | Sender address for password-reset emails | Password reset breaks |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_CLAIMS_EMAIL` | Web Push notifications | Push notifications silently no-op |

## Recurring maintenance

- `flask send-renewal-reminders` needs to run **every hour** (Render Cron
  Job `artha-renewal-reminders`, schedule `0 * * * *`), not once a day:
  each user picks their own reminder hour in their own timezone, and the
  job only sends to whoever's local hour matches on that run. A stale
  once-daily schedule means only users whose chosen hour happens to line
  up ever get notified. If push reminders stop arriving, check that this
  cron job still exists, still runs hourly, and ran successfully, before
  assuming it's an application bug.

## If the site is down

1. Check Render's dashboard/status for the service first. Most outages are
   a failed deploy or a Render platform issue, not application code.
2. Check the most recent deploy's build/migration logs if it looks like a
   bad push caused it.
3. A failed database migration is a specific, recurring real cause here —
   in particular, a new `Boolean` column migration whose default was
   autogenerated as `sa.text('1')`/`sa.text('0')` instead of `sa.true()`/
   `sa.false()` passes locally against SQLite and fails against Postgres
   on deploy (`psycopg2.errors.DatatypeMismatch`). Check the deploy logs
   for a migration failure specifically before looking anywhere else.
4. If nothing else resolves it, redeploying the last commit known to be
   good, from Render's dashboard, is the fastest rollback.

## Continuity risk

Code access and account access are two separate risks here, and they don't
carry the same weight.

**Repo access is intentionally solo.** Only one person has push access to
this codebase, by choice — nobody else can commit or push a code change,
ever, not just in an emergency. That's a real limitation (nothing gets
fixed at the code level if that person is unreachable), but it's not the
risk that determines whether Artha stays *online*: a hosted app keeps
serving its already-deployed code with zero GitHub access at all.

**Account access is what actually keeps the app alive**, and that's the
real single point of failure: one person currently holds every credential
this depends on — Render, the domain, and the API billing accounts
(Anthropic, Resend). None of that is written down here on purpose (a
public repo is not the place for who has access to what), but the risk is
worth stating plainly: if that person is unreachable, nobody else can
currently renew the domain, respond to a Render outage, or rotate a leaked
API key, regardless of who can see the code.

The fix for that part isn't code, and doesn't require adding anyone to
GitHub — it's making sure a trusted person has emergency access to those
specific credentials (most password managers, including 1Password, have a
built-in way to do this) before it's actually needed.
